# CVE-2017-14689 — Independent Reproduction and Root Cause Analysis

## Overview

This repository documents an independent reproduction and root cause analysis of **CVE-2017-14689**, a memory-safety vulnerability in **STDU Viewer 1.6.375** related to the processing of crafted DjVu files.

The publicly available vulnerability information identifies a crash at:

```text
STDUDjVuFile!DllUnregisterServer+0x328e
```

During our WinAFL-based fuzzing campaign, we independently discovered a crash at the same instruction and subsequently reproduced and analyzed the underlying data flow using **IDA Pro** and **WinDbg**.

Our analysis identifies a specific input-controlled 32-bit value that is propagated into an object field and subsequently used as a memory offset. A 32-bit integer wraparound during bounds validation allows the invalid offset to bypass the intended check, ultimately resulting in an out-of-bounds memory read and an `EXCEPTION_ACCESS_VIOLATION`.

> **Important:** We are not claiming this as a new vulnerability or requesting a new CVE. This repository is intended to provide an independent reproduction and additional technical analysis of the already assigned CVE-2017-14689.

## Crash Reproduction

The crash was reproduced in WinDbg using a crash input generated by WinAFL.

The faulting instruction was:

```asm
1000944E    mov eax, dword ptr [edi+esi]
```

At the time of the exception:

```text
EDI = 045C0000
ESI = E80306A6
```

Therefore, the effective address calculated by the instruction was:

```text
0x045C0000 + 0xE80306A6
= 0xEC5F06A6
```

The resulting memory access caused:

```text
EXCEPTION_ACCESS_VIOLATION (C0000005)
```

The crash location resolves to:

```text
STDUDjVuFile!DllUnregisterServer+0x328e
```

which matches the crash location publicly documented for CVE-2017-14689.

---

## Trigger Input

Analysis of the crash input identified the following four bytes at file offset `0x1F`:

```text
E8 03 06 A6
```

The DjVu parser function `sub_10010A10` reads these four bytes and combines them into the 32-bit value:

```text
E8 03 06 A6
        ↓
0xE80306A6
```

The implementation combines the first byte as the most significant byte.

The resulting value was observed in the target object's `+0x08` field:

```text
10026AD0  00000001 E80306A6 00000000
```

Thus:

```text
object + 0x08 = 0xE80306A6
```

The value is subsequently propagated to the `ESI` register before the vulnerable memory access.

---

## Root Cause Analysis

The critical validation logic is located in `sub_100093D0`:

```asm
10009437    sub eax, esi
10009439    cmp eax, 8
1000943C    jb  1000950B
```

At the time of the vulnerable execution:

```text
EAX = 0x0000633B
ESI = 0xE80306A6
```

The subtraction therefore produces:

```text
0x0000633B - 0xE80306A6
= 0x17FD5C95
```

The mathematical result would represent a negative difference. However, the operation is performed using 32-bit arithmetic, causing the result to wrap within the 32-bit integer range.

The subsequent comparison is effectively:

```text
0x17FD5C95 < 8
```

which evaluates to false.

Consequently, the `jb` branch is not taken.

WinDbg confirmed that the Carry Flag was cleared at the comparison, consistent with the observed branch behavior.

The invalid offset therefore passes the intended bounds check and is subsequently used by:

```asm
mov eax, dword ptr [edi+esi]
```

This results in an access to:

```text
0xEC5F06A6
```

and triggers the observed Access Violation.

The complete data flow reconstructed during dynamic and static analysis is:

```text
Crafted DjVu Input
        |
        v

        |
        v

        |
        v
0xE80306A6
        |
        v
Object + 0x08
        |
        v
ESI = 0xE80306A6
        |
        v
0x0000633B - 0xE80306A6
        |
        v
0x17FD5C95
        |
        v
Bounds check bypass
        |
        v
[EDI + ESI]
        |
        v
0xEC5F06A6
        |
        v
EXCEPTION_ACCESS_VIOLATION
```

This establishes a direct relationship between the bytes in the crafted DjVu file and the invalid memory address used at the crash site.

## Vulnerability Classification

Based on the observed behavior, the issue can be described as:

* **CWE-190 — Integer Overflow or Wraparound**
* **CWE-125 — Out-of-bounds Read**

The integer wraparound is the underlying validation flaw, while the resulting invalid offset causes the out-of-bounds memory access.

---

## Security Impact

The impact directly reproduced in our analysis is:

**Denial of Service / Application Crash**

An attacker-controlled DjVu file can cause STDU Viewer 1.6.375 to terminate abnormally when the vulnerable parsing path is reached.

We did **not** verify information disclosure or code execution in this analysis. Therefore, this repository does not claim those impacts.

## Fuzzing Harness

A custom C++ harness was developed to invoke the relevant parsing functionality inside `STDUDjVuFile.dll`.

The harness:

1. Loads `STDUDjVuFile.dll`.
2. Calculates the target function address from the module base and function offset.
3. Reads the mutated DjVu input into memory.
4. Constructs the minimum context required by the target parsing routine.
5. Passes the input buffer and its size to the target function.
6. Handles Windows SEH around the target invocation.

The harness was designed to avoid the overhead of fuzzing the complete GUI application and to focus coverage collection on the DjVu parsing component.

> The harness source is provided for reproducibility and research purposes. The exact target function offset is specific to the analyzed binary version.

## Mitigation

The vulnerable validation logic should avoid performing arithmetic that can wrap around before determining whether an attacker-controlled offset is valid.

A safer validation strategy is:

```text
if (offset > buffer_size)
    reject;

if (buffer_size - offset < required_size)
    reject;
```

The offset should be validated before subtracting it from the buffer size.

This prevents an excessively large attacker-controlled offset from causing integer wraparound and bypassing the bounds check.

Because STDU Viewer 1.6.375 is an old version, we have not independently verified the availability or applicability of an official vendor patch.

## Relation to CVE-2017-14689

This analysis should be considered an **independent reproduction and supplementary technical analysis of CVE-2017-14689**, rather than a newly discovered CVE.

The strongest confirmed overlap is the exact crash location:

```text
STDUDjVuFile!DllUnregisterServer+0x328e
```

which matches the publicly documented CVE-2017-14689 crash location.

We have not established that our generated input is byte-for-byte identical to the original PoC associated with the 2017 disclosure. Therefore, this repository does not claim that `E8 03 06 A6` is the original CVE-2017-14689 PoC payload.

Instead, our contribution is the independent reproduction of the crash and the reconstruction of the following previously undocumented-by-us data flow:

```text
DjVu input
→ 32-bit value parsing
→ object field +0x08
→ offset propagation
→ integer wraparound during bounds validation
→ bounds-check bypass
→ out-of-bounds read
→ Access Violation
```
